# Подключение MCP-клиента

## Codex: рекомендуемый stdio-режим

Для новой установки настройте Telegram и подключите Codex одной командой:

```shell
notification-mcp setup --client codex
```

Если личная конфигурация уже создана, достаточно:

```shell
notification-mcp connect codex
```

Обе команды по умолчанию регистрируют stdio-сервер. Codex запускает его как локальный процесс
и завершает вместе с MCP-соединением, поэтому `notification-mcp start` не требуется. Перезапустите
Codex и проверьте `/mcp`, затем отправьте `/start` своему Telegram-боту.

Команда сохраняет остальные настройки Codex и повторяется без создания дубликата. Если запись
`notifications` уже содержит другой транспорт или отключена, файл остаётся неизменным. Выполните
`codex mcp remove notifications` и повторите подключение. Путь учитывает `CODEX_HOME`, по
умолчанию используется `~/.codex/config.toml`.

Для ручного добавления получите готовый блок:

```shell
notification-mcp client-config codex --transport stdio
```

Он содержит абсолютные пути к установленному Python и личной конфигурации. Токен Telegram
в конфиг MCP-клиента не передаётся. Формат соответствует
[официальной документации OpenAI](https://learn.chatgpt.com/docs/extend/mcp?surface=cli).

## Codex: токен из окружения без сервисного конфига

Этот режим предназначен для одного Telegram-бота с настройками доставки по умолчанию. Создайте
пользовательскую переменную `TELEGRAM_BOT_TOKEN` в операционной системе. Не передавайте токен
аргументом командной строки: он может остаться в истории shell.

Зарегистрируйте профиль:

```shell
notification-mcp connect codex --token-env
```

Для другого имени переменной:

```shell
notification-mcp connect codex --token-env MY_TELEGRAM_TOKEN
```

Команда не читает и не создаёт `config.toml`. Для стандартного имени она добавляет:

```toml
[mcp_servers.notifications]
command = "АБСОЛЮТНЫЙ_ПУТЬ_К_PYTHON"
args = ["-m", "notification_mcp", "serve", "--transport", "stdio"]
env_vars = ["TELEGRAM_BOT_TOKEN"]
```

`env_vars` содержит только разрешённые имена: значения Codex берёт из своего локального
окружения. После создания или изменения пользовательской переменной полностью перезапустите
Codex. Готовый блок без регистрации можно получить так:

```shell
notification-mcp client-config codex --token-env
```

Если запись `notifications` уже существует в другом режиме, команда оставит её без изменений.
Выполните `codex mcp remove notifications` и повторите подключение. SQLite-очередь и привязка
Telegram сохраняются в `var` рядом с обычным личным конфигом, но сам TOML не требуется.

Режим намеренно ограничен одним Telegram-каналом. Для фиксированного `chat_id`, нескольких
каналов, маршрутизации событий или нестандартных параметров доставки используйте `config.toml`.

## Codex: фоновый HTTP-режим

Он нужен, если один процесс должен обслуживать несколько MCP-клиентов:

```shell
notification-mcp setup
notification-mcp start
notification-mcp connect codex --transport http
notification-mcp test
```

При стандартном порте в Codex добавляется:

```toml
[mcp_servers.notifications]
url = "http://127.0.0.1:8765/mcp"
```

HTTP-сервер продолжает работать после закрытия Codex. После перезагрузки компьютера его нужно
запустить снова.

## Другие клиенты

В приложении с поддержкой **Streamable HTTP** укажите `http://127.0.0.1:8765/mcp`.
Для JSON-конфигурации выполните:

```shell
notification-mcp client-config json
```

Программа выдаст блок `mcpServers.notifications`. Названия разделов зависят от клиента:
если он использует форму добавления сервера, выберите Streamable HTTP и вставьте URL.
При изменении `server.port` команда выдаёт актуальный адрес.

## stdio для других клиентов

```shell
notification-mcp stop
notification-mcp client-config json --transport stdio
```

Полученный блок содержит абсолютные пути к установленному Python и конфигурации, поэтому не
зависит от `PATH` и текущей папки клиента. Вставьте его в настройки MCP-приложения.

Клиент также может запустить сервер без конфига той же командой, что приведена выше, если он
передаёт процессу `TELEGRAM_BOT_TOKEN`. Поле, которым клиент наследует или задаёт окружение,
зависит от конкретного приложения; `env_vars` в этом виде является настройкой Codex.

Сервер будет работать, пока клиент поддерживает процесс. Для завершения отключите MCP-сервер
в клиенте или закройте клиент. `start`/`stop`/`status` управляют отдельным фоновым HTTP-сервером;
процесс stdio ими не управляется. `serve` в терминале завершается через Ctrl+C.

Нельзя одновременно использовать HTTP и stdio с одной базой. Несколько клиентов, запускающих
свой stdio-процесс, также конфликтуют. Для общего слоя нескольких приложений используйте HTTP.

## Команды агенту

Проверка подключения:

> Вызови notify сервера notifications: сообщение «Проверка подключения», событие info.
> Затем проверь доставку через notification_status по полученному ID.

Чтобы не повторять поручение в каждой задаче, добавьте в личный или проектный `AGENTS.md`:

> Когда требуется моё решение, вызывай notify с событием action_required.
> Когда работа готова к проверке — review_requested. При ошибке, требующей внимания — error.
> Указывай проект и задачу в source, кратко описывай нужное действие.
> Повторный вызов для того же события должен использовать прежний idempotency_key.
> Не называй queued доставкой: подтверждённое состояние — sent.

Подключение MCP само по себе не создаёт slash-команду и не запускает наблюдение за задачами.
Агент вызывает инструмент по поручению пользователя или своим постоянным инструкциям.
